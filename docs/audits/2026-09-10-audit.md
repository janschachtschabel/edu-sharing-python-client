## Method

Every claim was measured, not read. Static: `ruff check .` (project config) and
the extended lens (`S,B,PERF,SIM,PL,C4,ASYNC`), `mypy --strict`, coverage,
`pip-audit`, and the generated-layer build. Dynamic: the full offline suite, and
the live and write suites against staging with the password loaded from the
gitignored `.env` and masked in output. The three doc-drift findings were each
reproduced against the source before the fix, and each fix verified by the
existing documentation guards.

keep the documentation and the generated layer honest all still bite. The
finalization pass fixed three measured documentation defects, brought the
changelog into one ordered set with the last two rounds recorded, and closed

## Findings

### Environmental, not a code defect — live download returns 403

Six of the live/write tests fail today, all on `content.download()` against
staging: `PermissionDeniedError HTTP 403` from the `eduservlet/download`
servlet. Measured with a throwaway folder under the test account (`SC25-14`):
**the parent node's own download 403s too**, although the node's `access` array
lists `DownloadContent`, and the upload itself succeeds (`has_content` true,
hash present). Every non-download write test passes.

The obvious suspect was our own change: F01 (`3875df1`, the day before)
switched the HTTP client's cookie jar off, and a servlet outside the REST API
might well authenticate by session. **Tested and refused.** An independent
`httpx` client with no cookie restriction whatsoever, carrying the same Basic
credentials, receives the identical 403 — byte for byte the same 247-byte body
as a fully anonymous request. No session is involved at all: the instance
answers `validateSession` with 404 and sets no cookie.

**And there is no other route to take.** The specification carries no `GET` for
binary content — `/node/v1/nodes/{repository}/{node}/content` is `POST` only,
which is why a `GET` on it answers 405, and the only other content routes are
`textContent` and the upload. `downloadUrl` is the one way a file can be
fetched, so the library is doing the only thing available to it.

**The test is left failing rather than weakened** — a test made green by
lowering its bar would hide the day this stops being environmental.

#### Correction, 2026-09-10 — the cause named here was wrong

This section concluded "the servlet is simply not honouring Basic auth for
**this account**", and asked for a look at the staging account's servlet-level
rights. Both were wrong, and wrong in the way this audit's own Nachtrag warns
about: the conclusion was drawn from one kind of node — one we had just
uploaded ourselves — and generalised to the account.

The third review asks for exactly the measurement that settles it (its section
2: "a known, readable test document with the same identity, across metadata,
text and download access"). Run on 2026-09-10:

| Probe | Result |
|---|---|
| A foreign, **public** document, anonymous | metadata, `text()` and `download()` all succeed — 5 867 B |
| The same document, **with our credentials** | identical — 5 867 B |
| Our own **private** upload, with credentials | `403`, and still `403` after 69 s — not an indexing delay |
| `text()` on that same private node | succeeds, 25 characters |
| That same node after `publish()` | `download()` returns the bytes — **and so does a guest** |

So the servlet is not refusing *this account*. It does not authenticate **at
all**: it serves what is publicly readable and refuses everything else, whoever
asks. That is also why the anonymous and the Basic-authenticated request came
back byte-identical earlier — to the servlet they are the same request. The
account's rights were never the question, and no one needs to go looking at
them.

**And it has not always been this way.** `test_volltext_gibt_es_nicht_fuer_jeden_dateityp`
carries the line `assert await node.content.download() == inhalt` on a private,
freshly uploaded node, and git dates it to `0aef368`, 2026-08-27. Assertions in
this repository are measured rather than guessed, so on that day the servlet
handed a private node's bytes to its owner. Fourteen days later it does not.
This is a change on the staging side within that window — worth raising with
whoever runs the instance, and a different question from "the account lacks a
right", which is what the paragraph above used to send them looking for.

What the earlier text got right stands: it is not a library defect, the
specification offers no second route, and the failing tests stay failing. What
changes is what a **caller** must be told — `download()` now documents that it
reaches public content only, and points at `text()` for a private node. A live
test pins the three measurements against each other
(`test_das_download_servlet_liefert_nur_oeffentliches`), so the day the
instance changes its servlet back, something goes red and says so.

### Fixed in this pass

- **A documented call that does not exist.** The Structure table in both
  READMEs listed `collection()` as a resource-layer method beside `search()`
  and `node()`. Measured: neither `Repository` nor `AsyncRepository` has a
  `collection` attribute — a collection is read with `find_collections()` or
  `node()` (a collection is a `ccm:map` node). Corrected to `find_collections()`.
- **A stale example range.** The usage skill pointed at `docs/examples/01…17`
  in both languages; there are twenty-one. Corrected to `01…21`.
- **The changelog had drifted from the code.** The `[Unreleased]` block carried
  two full sets of `### Added/Changed/…/Fixed` (a second commit appended rather
  than merged), and none of the 2026-09-09 rounds were recorded — measured,
  `facet_meta`, `source_url`, `truncated_by`, `variants_total`, the
  breadth-first walk and the cookie refusal appeared nowhere. The block is now
  one ordered set, and eleven entries record the user-facing behaviour of the
  two rounds and the section-7 follow-up. No entry was dropped in the merge
  (77 → 77 before the additions, verified by title).
- **Three flows had no runnable example.** Of 26 flows, `find_skills`,
  `pick_skill` and `accept_suggestion` were exercised nowhere. `find_skills`
  and `pick_skill` (find a skill by task, not by collection) were added to
  `21_skills.py` — verified anonymously against staging, and the query was kept
  short on purpose because edu-sharing ANDs every word (a five-word phrase
  found nothing, `"Fragen generieren"` found one). `accept_suggestion` was
  added to `16_editorial.py`, where it completes the existing lesson: `decide()`
  marks a proposal but does not write it (`keywords: []`), while
  `accept_suggestion` writes, reads back and marks (`keywords: ['Mitose']`) —
  verified live with credentials, exit 0, throwaway folder removed.

## Nachtrag — a third review, later the same day

A third-party review of `4b6ec40` (the head this pass produced) confirmed the
repairs hold: **F01–F15 all pass, R01–R09 are corrected**, CI green across all
eight jobs, 2 227 tests passing on its own checkout. It then found two defects
this audit did not.

Both were reproduced here before anything was touched, and both were real:

- **A01 · `grant()` did not check what the authority already had.** The first
  comparison reads the newly requested permissions alone, and the shared
  preservation check is told to skip this authority — between the two, the old
  entry fell through. Measured: `alice:[Read]` plus `grant("alice", "Write")`
  against a repository that stores only `Write` returned `True`. The foreign
  entries and the inheritance stayed intact, so no other check saw anything.
  This audit's own line "the guards that were added to keep the documentation
  and the generated layer honest all still bite" was true and beside the
  point: the guard that was missing had never been written.
- **A02 · the duplicate check repeated credentials from the caller's own
  address.** A dummy password inside a malformed URL came back in the
  `ValidationError`, in the `if_exists="return"` warning and in the
  `if_exists="raise"` `ConflictError` — before any request went out. Measured
  here at **six** sites, not the three reported: the "not an http(s) address"
  path leaks the same way, and so does the message for a hit that was found.

Both are fixed, each with its guard proven by mutation, and each with
counter-checks so the fix cannot be green by refusing everything.

Two public docstrings (`D01`) had also stayed behind their repairs and now
say what the code does. `R10` was re-measured and is unchanged; it remains the
documented boundary, not a repair — see the corrected count above.

**What this costs the verdict.** "Release-ready" was written of a state that
carried a P2 ACL defect and a P2 credential leak. The finding that matters for
the next round is not either bug: it is that this audit measured the guards it
knew about. `pip-audit`, `mypy --strict`, coverage and a green suite say
nothing about a promise no test was ever written for — and A01 was exactly
that, a sentence in a docstring with nothing behind it. The plan for that
round is [2026-09-10-drittpruefung](../plans/2026-09-10-drittpruefung.md).
