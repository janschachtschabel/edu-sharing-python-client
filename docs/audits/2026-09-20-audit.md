## 1. Executive summary

The library is in good health and its core promises hold under inspection: the
credential boundary, the SSRF rules, the read-back after every write, the
refusal to follow a redirect, the bounded download. Three prior audit rounds
are visible in the source — nearly every rule carries the measurement that
produced it — and the guard suite now watches the documentation as closely as
the code. Nothing found this round is a vulnerability.

The three risks worth acting on are elsewhere. **The install command the new
README prints for the tagged release cannot work**: it points at a repository
that has no tags. **The MDS cache bought isolation at a price nobody measured**
— 18 MiB and 0.3 s of blocked event loop per `load()` or `fields()` call,
unbounded in the number of locales. And **two of the five service clients skip
the base-address check the other three perform**, so a mistyped gateway address
is accepted, sent to, and only reported after the full retry budget.

Single most important action: make the two repositories one story (which one
users install from, where releases are tagged, where a vulnerability is
reported) and fix the install instruction accordingly.

## 2. Overview

**Stack and purpose.** Python ≥ 3.11, async-first over `httpx`, two runtime
dependencies (`httpx`, `attrs`). A client for edu-sharing repositories with
four sibling services beside it: the b-api LLM gateway, its template mode, the
text-extraction service and the metadata agent. Above the plain API sit typed
DTOs, composed *flows* (one use case per call), an agent surface (sanitising,
safety, tool results) and a blocking facade generated by hand in `_sync.py`.
A skill bundle under `.claude/skills/` teaches an LLM to use it.

**What was read.** The whole hand-written layer, with line-by-line attention to
`transport.py`, `auth.py`, `urls.py`, `errors.py`, `extraction.py`,
`bapi/client.py`, `bapi/templates.py`, `bapi/passthrough.py`,
`metadata_agent.py`, `metadata.py`, `agent/*`, `nodes_write.py`, `_http.py` and
the three newest flow modules. The test suite was read where it makes a claim
about behaviour (the doc guards, the sync surface guard, the composed flows).

**What was not read.** The 1 131 generated files, except the guards that seal
them; `docs/` beyond the parts a finding touches; the example scripts beyond
the two the README asks a new user to run.

**Numbers.** 19 133 hand-written lines across 76 modules; 26 modules above 300
lines, 9 above 500 (largest: `_sync.py` 890, `bapi/client.py` 683, `nodes.py`
607). 2 698 offline tests in 93 modules. Eight CI jobs.

## 4. Verdict

**Conditional — and the conditions are small.**

For use as a library the state is sound: reading, writing, the flows, the agent
surface and the gateway all rest on rules that were measured rather than
assumed, and the suite that proves it runs on every push across five platform
legs.

Two conditions before this is handed to people who are not the author:

1. **`DOC-20-1`** — the printed install command for the tagged release fails
   for everyone who runs it. It is the first command a careful new user runs,
   and it is in both languages.
2. **`COR-20-1`** — fix before anyone puts the extraction service behind an
   agent. One malformed field from that service leaves the library's error
   contract and crashes the tool call.

Everything else on this list is improvement, not a blocker.

### DOC-20-1 🟠 the install command for the tagged release cannot work

```
File:     README.md:380-398, README.de.md:385-403 (also README.md:39, README.de.md:44)
Problem:  Both READMEs tell users to install from
          github.com/openeduhub/edu-sharing-python-client@v0.2.0. That
          repository has no tags at all.
Why:      pip resolves a `@ref` by asking the remote for it. There is nothing
          to resolve.
Impact:   Four printed commands (two per language) fail with "Could not find a
          tag or branch 'v0.2.0'". The note "Not @v0.1.0" names a second tag
          that is equally absent, and README.md:39 states "The existing tag
          remains v0.2.0" about a repository where it does not exist.
Measured: `git ls-remote --tags https://github.com/openeduhub/edu-sharing-python-client`
          -> empty. `git ls-remote <that url> v0.2.0` -> 0 refs. The same
          command against `janschachtschabel/...` returns v0.0.1, v0.1.0, v0.2.0.
Fix:      Decide where releases live (see DOC-20-2). If it is openeduhub, tag
          `main` there -- the histories are unrelated, so the old tags cannot
          simply be pushed -- and point the section at that tag. Until a tag
          exists there, the honest instruction is `@main` plus one sentence
          saying no tagged release is published yet.
```

### PRF-20-1 🟡 every metadata call deep-copies 18 MiB

```
File:     src/edusharing/metadata.py:44-45 (cache hit), 54 (store), 64-66 (fields)
Problem:  `load()` returns `copy.deepcopy(entry[1])` on every hit, and
          `fields()` goes through `load()` before filtering 235 widgets out of
          the document.
Why:      The isolation promise ("Caller changes to returned dictionaries never
          modify the cached definition") is right; paying it in full on every
          call is what was never measured against a real metadata set.
Impact:   Measured live against staging (`mds_oeh`, 235 widgets, 17.9 MiB of
          JSON): first load 1.07 s; every further load 0.28-0.31 s with a 21 MiB
          allocation peak; `fields()` costs the same 0.27 s to hand back 235
          small dicts. That is 0.3 s of *blocked event loop* per call in an
          async service -- the cache saves the network and gives the CPU back.
Fix:      Keep the widget list as its own cached, already-filtered structure so
          `fields()` copies only what it returns; for `load()`, either hand out
          a read-only view or document the cost and let the caller ask for the
          raw object once.
```

### PRF-20-2 🟡 the MDS cache grows without bound, keyed on a caller-supplied string

```
File:     src/edusharing/metadata.py:31, 41, 54, 68-72
Problem:  One entry and one `asyncio.Lock` per distinct `locale`, never evicted.
          Only `clear_cache()` empties them, and it drops the lock dict while a
          load may still hold one of its locks.
Why:      `locale` is a free string from the caller. A service that forwards a
          request's Accept-Language has as many keys as it has visitors.
Impact:   18 MiB per distinct locale (measured, see PRF-20-1) with no ceiling --
          ten locales is ~180 MiB held for the lifetime of the repository
          object. After `clear_cache()`, an in-flight load holds a lock nobody
          else can see, so a concurrent caller fetches a second time; the
          `_generation` guard keeps that from corrupting the cache, so this is
          load, not corruption.
Fix:      Bound the locale cache (a small LRU is enough) or validate the locale
          against the set the instance offers; keep the lock table out of
          `clear_cache()`.
```

### COR-20-1 🟡 a malformed status from the extraction service escapes the error contract

```
File:     src/edusharing/extraction.py:448, 461 (in `_result`)
Problem:  `int(detail.get("status") or 0)` and `int(body.get("status") or 0)`
          trust a field from a foreign service to be numeric.
Why:      `text_of` documents exactly two outcomes -- an `ExtractedText`, or an
          `EduSharingError` -- and `agent.result.as_result` (agent/result.py:62-67)
          re-raises anything that is not an `EduSharingError`, on purpose:
          "Defects stay loud."
Impact:   Measured against a mocked service: a 200 carrying `"status": "OK"` and
          a 424 carrying `"status": "424 Failed"` both raise
          `ValueError: invalid literal for int() with base 10`. Behind an agent
          that is an unhandled crash of the tool call instead of
          `ToolResult(ok=False)`.
Fix:      A three-line `_as_int(value) -> int` that answers 0 for anything
          unreadable -- the same shape `metadata_agent.py:334-335` already uses
          (`except (TypeError, ValueError, OverflowError)`) and that
          `errors._parse_body` and `bapi/client._error` (F13) apply to the
          object shape.
```

### SEC-20-1 🟡 two of the five clients accept an unusable service address

```
File:     src/edusharing/bapi/client.py:176-181, src/edusharing/bapi/templates.py:141-147
Problem:  Both run `refuse_userinfo(...)` and then `base_url.rstrip("/")`.
          No scheme check, no host check, no query or fragment check.
Why:      The other three do it. `TextExtraction._check_base`
          (extraction.py:414-433) and `MetadataAgent._check_base`
          (metadata_agent.py:338-352, whose docstring reads "as TextExtraction
          demands") refuse all of it; `Transport` goes through
          `normalize_repository_url`. These two are the clients that put an
          `X-API-KEY` on every request, and client.py:76-80 says why the
          address matters: "a wrong one sends your API key to a host you did
          not choose."
Impact:   Measured: `BildungsAPI(key, base_url="ftp://gw.example.test")` is
          accepted and the request is built and sent with the key header;
          `"https://gw.example.test/?x=1"` produces
          `https://gw.example.test/?x=1/api/v1/llm/academiccloud/models`, where
          the route has become part of a query string; a bare host ends in
          `ValueError: unknown url type` -- a stdlib exception, outside the
          library's contract, after the full retry budget. `BapiTemplates`
          accepts all three identically.
Fix:      Move `_check_base` into `urls.py` (it is already duplicated once) and
          call it from both constructors.
```

### COR-20-2 🟡 a repository URL with a query or fragment is silently mangled

```
File:     src/edusharing/urls.py:64-120 (`normalize_repository_url`), 112 (the count)
Problem:  The function refuses four malformed shapes loudly and reads the fifth
          as part of the path.
Why:      The `/edu-sharing` counter uses the lookahead `(?=/|$)`, which does
          not treat `?` or `#` as an end of segment.
Impact:   Measured:
            https://repo.example.test/?x=1            -> https://repo.example.test/?x=1/edu-sharing
            https://repo.example.test#frag            -> https://repo.example.test#frag/edu-sharing
            https://repo.example.test/edu-sharing?x=1 -> https://repo.example.test/edu-sharing?x=1/edu-sharing
          The last is the doubled `/edu-sharing` this function exists to refuse,
          produced by the function itself. Every call then addresses something
          that can never answer, with no message anywhere saying why -- exactly
          the failure mode the module docstring opens with.
Fix:      Refuse a query or fragment with the wording the deep-link refusal
          already uses, or strip both before normalising. A repository base has
          neither.
```

### MNT-20-1 🟡 the b-api model cache is handed out by reference

```
File:     src/edusharing/bapi/client.py:248-283 (`models`, in `aus_dem_cache`)
Problem:  The cache hit returns `self._models_cache[1]` -- the stored list
          itself, not a copy.
Why:      The same class of defect was found and fixed for the vocabulary cache
          in the 0.3.0 round (F02, "Rueckgaben veraendern den Vokabular-Cache")
          and is guarded in `MetadataCatalog`. This one was not revisited.
Impact:   Measured: `models = await llm.models(); models.clear()` empties the
          cache; the next `models()` returns `[]` without a request. Under
          `CACHE_FOREVER` it never recovers, and `chat()` with automatic model
          selection then raises "No ready text model at provider ...". Any
          in-place `sort()` or `remove()` by a caller changes what every later
          call chooses from.
Fix:      `return list(gemerkt)`. `Model` is frozen, so a shallow copy is enough.
```

## 6. All findings

### Security

* **SEC-20-1 🟡 two of five clients accept an unusable base address** — see §5.
* **SEC-20-2 🟢 spot-checks of the prior rounds' closures, all holding** —
  `auth.py:142-189` reports shape and length, never a value; `urls.py:145-172`

### Logic & Correctness

* **COR-20-1 🟡 malformed extraction status escapes the error contract** — see §5.
* **COR-20-2 🟡 repository URL with query or fragment silently mangled** — see §5.
* **COR-20-3 🟢 an `assert` carries a type invariant** — `_decoding.py:67`

  next line raises `AttributeError` on `None` instead. The comment says the
  decoder is selected before any data is inflated, which is true today; the
  cost of making it an explicit `if ... raise` is one line.

### API

* **SEC-20-1** is also an API finding: the failure surfaces as a stdlib
  `ValueError` after the retry budget rather than as an `EduSharingError` at
  construction.

### PRF-20-1 came out differently once it was measured

The finding read `fields()` as copying 18 MiB to hand back 235 small dicts.
Measured before the change: those 235 widgets **are** the document — 17.41 of
17.5 MiB, because each carries its vocabulary. Nothing can be copied less
without taking data away, so there was no optimisation to make there.

The faster route was real and was rejected on its numbers. On `mds_oeh`:

```
copy.deepcopy(...)              0.275 s   21 MiB peak
json.loads(json.dumps(...))     0.173 s   50.7 MiB peak
```

40 % faster, and it holds the serialised string and the parsed result at once.
A library runs inside someone else's process, where a tenth of a second is
theirs to plan around and an allocation spike is not. Both numbers now stand in
`metadata._copy`, and `load` states what a call costs, so the next reader does
not have to measure it again — which was the part of the finding that was
right: the cost was real and nowhere written down.

### ARC-20-2 is not a defect and was not treated as one

Nine modules above 500 lines, each with one responsibility and each readable
top to bottom. `bapi/client.py` is the one with two jobs in it — model policy
and HTTP — and splitting it is a contained refactor worth doing on its own,
with its own review, not inside a round of fixes for unrelated findings. It
stays on the roadmap.

### ARC-20-2 — one seam, not two

`bapi/client.py` went from 778 lines to 595; `bapi/choice.py` holds what
decides *which* model answers — a group name or an explicit list, the ranking
when the caller left the choice open, the cap on guessing, the switch to the
next candidate. `chat` and `passthrough.respond` reach it the way `passthrough`
has always been reached: a free function with `api` as its first argument.

`_request` stayed on the class, and that was a decision rather than an
omission. Seven call sites ask for it, four of them in `passthrough`, where
`api` is an opaque handle and `_request` its one verb; moving it off would
force every collaborator to import a transport module **and** pass the object
anyway. 595 lines is still past the threshold, which is recorded here rather
than explained away — what remains is one class with its construction, its
model cache and its HTTP.

Behaviour was held by comparison, not by claim: 2 755 tests before the move
and 2 755 after, with no test touched. That a green suite proves nothing by
itself was checked two ways — `DEFAULT_MODEL_ATTEMPTS = 1` reddens two tests
in `test_bapi_client.py`, and making `first_that_answers` raise reddens two in
`test_bapi_passthrough.py`, so both callers demonstrably arrive at the new
module.

Four guards caught the move. Two ARCHITECTURE files must name every module,
and the READMEs' warning table must name the module that warns — which had
become `bapi/choice.py`, so the old row was not merely incomplete but false.
`test_docs_inventories` asks both directions, which is why it said so.

### DOC-20-2 was fixed, and went stale again

`SECURITY.md` read `main` (0.3.0) while the project shipped 0.3.4. The fix on
2026-09-20 corrected the number and nothing held it there; four releases later
the table said what it had said before, and above it stood "there is no tagged
release beside it yet" — true when written, false since the tags were pushed.

A number in a document that nobody recomputes becomes wrong without ceasing to
look convincing. That is the sentence the README tag guard was written on, and
it applies here unchanged: `tests/test_docs_home.py` now holds every line the
table marks supported to the version in `pyproject.toml`, and fails a line
that names no version at all — otherwise the cheapest way to pass would be to
stop saying which version is meant.

The release checklist carried the same decay in two more places nothing was
watching: step 6 spelled out `git tag -a v0.3.0` as its worked example and was
