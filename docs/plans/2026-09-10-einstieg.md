# Einstieg — kann jemand die Bibliothek schnell installieren und benutzen?

Die Frage kam von außen und ist keine Prüfbericht-Frage: *wie installiert und
benutzt jemand das, wenn es auf GitHub liegt?* Beim Nachmessen fiel neben
Doku-Lücken ein echter Bibliotheksfehler an.

## Gemessen

| Probe | Ergebnis |
|---|---|
| `uv pip install git+https://github.com/…/edu-sharing-python-client` in ein leeres 3.12-venv | funktioniert — `0.1.0` von `c92b7dd`, dazu nur `httpx` und `attrs` |
| Rauchprobe danach, anonym gegen Staging | `about().repository_version` → `11.0`, Suche → 3 Treffer |
| dieselbe Installation mit `@v0.1.0` | zieht `80f5a1f` vom 02.09. — **203 Commits hinter `main`**, und noch mit `python-dateutil`/`six` |
| `repo.vocab.resolve(...)` auf dem **synchronen** `Repository` | gibt eine **Coroutine** zurück |
| `await`-Blöcke je README | 16 von 39, davon 12 auf einer Fläche, die synchron kann |
| erstes Codebeispiel im README | Zeile 101 — davor ~85 Zeilen Begründung |

## Reihe A · Der Bibliotheksfehler

Erst hatte ich nur `vocab` gemessen. Die vollständige Durchsicht — jedes
öffentliche Unterobjekt der asynchronen `AsyncRepository` gegen sein
synchrones Gegenstück — findet **vier**:

| Unterobjekt | ohne Spiegel | in REFERENCE dokumentiert |
|---|---|---|
| `repo.vocab` | `resolve`, `resolve_all`, `suggest`, `values` | 9 Erwähnungen |
| `repo.collections` | `add`, `create`, `find`, `remove`, … | 6 |
| `repo.nodes` | `get`, `children`, `create` | 4 |
| `repo.searcher` | `search` | 2 |

- [x] **Vier öffentliche Unterobjekte sind aus synchronem Code unbenutzbar.**
      Sie reichen das asynchrone Objekt durch, und der Aufrufer bekommt eine
      Coroutine. `SyncFlows`, `SyncNode`, `SyncRelations`, `SyncComments`,
      `SyncPeople`, `SyncSkills`, `SyncSuggestions`, `SyncNodePermissions`,
      `SyncNodeContent`, `SyncNodePage` und `SyncChildObjects` gibt es — diese
      vier fehlen. Das ist keine Doku-Frage, und es erklärt, **warum** die
      Beispiele überall `await` benutzen: die synchrone Fassade trägt sie nicht.
- [x] **Die Wache hat eine Ebene über sich selbst eine Lücke.**
      `test_sync_surface.py` ruft jede Coroutine-Methode jedes Paares auf —
      gründlich. Aber die Liste der Paare ist **handgepflegt**, und diese vier
      stehen nicht darin. Genau die Fehlerart, gegen die die Datei geschrieben
      ist, eine Ebene höher. Sie bekommt eine Prüfung, die die Paare nicht mehr
      glaubt, sondern selbst aufzählt.

## Reihe B · Der Einstieg

- [x] **Ein Schnellstart direkt hinter „Installing".** Installieren, eine
      Suche, fertig — synchron, ohne `await`, in einem Bildschirm. Heute steht
      das erste Codebeispiel hinter dem ganzen „Why"-Kapitel, und es zeigt
      `about()` und `whoami()`: Diagnose, nicht das, wofür jemand kommt.
- [x] **Der Tag-Hinweis fehlt.** Wer `@v0.1.0` pinnt — der naheliegende Griff,
      wenn man auf GitHub eine Release-Seite sieht — bekommt den Stand vor
      sämtlichen Prüfrunden: kein F01–F15, kein R01–R09, kein A01/A02. Das
      muss dort stehen, wo installiert wird.
- [x] **12 Blöcke je README benutzen `await` auf der Repository-Fläche**,
      obwohl der README mit dem synchronen `Repository` einsteigt. Gemessen:
      `repo.raw.json` ist dort keine Coroutine — wer das kopiert, bekommt einen
      Fehler. Sie werden synchron geschrieben.
- [x] **4 Blöcke je README sind echt async-only** (`BildungsAPI` 15 Coroutinen,
      `TextExtraction` 8, keine öffentliche Sync-Methode; dazu Gateway und
      Metadaten-Agent). Sie behalten `await` und bekommen **eine** Kommentar-
      zeile, die den Rahmen nennt. Kein `async def main()` drumherum: das
      schöbe 16 Blöcke um zwei Ebenen ein, und Verschachtelung ist genau das,
      was hier nicht sein soll.

## Reihe C · Eine Zusage, die nicht stimmt

- [x] **„`AsyncRepository` is the same surface"** (README) und **„the same,
      `async`"** (REFERENCE). Für `vocab` stimmt das heute nicht. Nach Reihe A
      stimmt es — dann ist der Satz belegt statt behauptet.

## Was nicht dazugehört

- **Einen `v0.2.0`-Tag setzen.** Das ist eine Freigabe, keine Reparatur, und
  gehört dem Maintainer. Der Hinweis im README beschreibt den Ist-Zustand,
  ohne ihm vorzugreifen.
- **REFERENCE auf synchron umstellen.** Die Referenz ist bewusst async-first
  (`AsyncRepository(url, ...)` heißt dort „the same, `async`"), und ihre
  Aufgabe ist Nachschlagen, nicht Einstieg. Sie bekommt nur die
  `vocab`-Korrektur.

## Vorgehen

Reihe A test-first und durch Mutation belegt. Reihen B und C sind Doku; ihr
Beleg ist, dass jedes geänderte Beispiel wirklich läuft — die synchron
geschriebenen werden gegen die Instanz ausgeführt, nicht nur gelesen.

## Ergebnis

| Schritt | Beleg |
|---|---|
| Reihe A · Wrapper | Neue Wache benennt vor der Reparatur alle vier mit 13 Methoden; danach grün. Mutation an `children`: gibt sie die Seite roh zurück, fällt genau der neue Test. |
| Reihe A · live | Anonym gegen Staging: `vocab.resolve`, `vocab.suggest` (416 Werte), `vocab.values`, `searcher.search`, `collections.find`, `nodes.get` — alles blockierend, keine Koroutine. |
| Reihe B · Blöcke | 9 je README synchron geschrieben (nicht 12 — `as_result` nimmt ein Awaitable, `plan_update` ist async, ein dritter nutzt `TextExtraction`), 7 gekennzeichnet. **0 von 40 Blöcken benutzen jetzt `await` ohne Marke.** |
| Reihe B · Beleg | 66 synchrone Blöcke kompiliert, 0 Beanstandungen; vier davon wörtlich gegen die Instanz ausgeführt und geantwortet. |
| Reihe B · Schnellstart | Vorher ausgeführt — und dabei gelernt, dass `subject=` ohne `metadataset="mds_oeh"` mit `400` scheitert. Steht jetzt so im Beispiel. |
| Suite | 2266 bestanden, ruff und `mypy --strict` sauber. |

### Zwei Funde nebenbei

**Der `/children`-Zweig des Mocks war toter Code.** Er prüft `url.endswith("/children")`, aber `url` ist `str(request.url)` und trägt `maxItems` und `skipCount` — er endet nie auf `/children`. Deshalb lief `test_blaettern_synchron` seit jeher über eine leere Liste: grün, ohne etwas zu prüfen. Aufgefallen ist es nur, weil mein neuer Test `assert seite.nodes` mitbringt und sich weigerte, leer durchzugehen.

**Die Seitenumhüllung stand zweimal da.** `Repository.children` und `SyncNodes.children` bauten dieselbe `ChildPage` um. Seit die Knotenschicht blockiert, ruft die kürzere die längere.

### Die Lehre, zum vierten Mal in dieser Sitzung

A01 war eine Zusage ohne Test. Review-Befund 1 war eine Erklärung ohne Beweis für den Randfall. Der Download-403 war eine Ursache aus einer einzigen Stichprobe. Und „`AsyncRepository` is the same surface" war eine Symmetriezusage, die für vier von neun Flächen nicht galt — nachlesbar in zwei Sprachen, seit dem ersten Tag des Repositoriums (`0c91dd5`, 27.08.2026). Es hat eine Frage von außen gebraucht, um sie zu prüfen: *wie benutzt das eigentlich jemand?*

## Nachtrag · 11.09.2026 — der Rest der Doku

README war fertig; offen waren REFERENCE, FLOWS, der Nutzungs-Skill,
ARCHITECTURE und die 21 Beispieldateien.

**Verschachtelung** ist nirgends ein Problem. Diesmal mit `ast` über die echten
Blockanweisungen gemessen, nicht über Einrückung (die hatte im README
Fortsetzungszeilen als „7 Ebenen" gezählt): kein Codeblock in keinem Dokument
erreicht Tiefe 3, und keine der 21 Beispieldateien hat drei Ebenen im Rumpf
einer Funktion. Die längste Funktion hat 46 Zeilen.

**Konvention.** FLOWS (Zeile 27) und Skill (Zeile 56) sagten schon, dass ihre
Beispiele für `AsyncRepository` geschrieben sind — und das stimmt seit gestern.
REFERENCE sagte es nicht; jetzt steht der Satz oben. Die nur-asynchronen Blöcke
tragen eine eigene Marke: 7 in REFERENCE, 3 im Skill, je Sprache. FLOWS braucht
keine: seine sechs nur-asynchronen Blöcke sind `asyncio.gather`, und das rahmt
sich selbst.

Gemessen: gesetzt `0`, angekommen `3600.0`. Vorher ging es. | den Docstring-Satz „`__getattr__` keeps the settings reachable" gegen die dokumentierte Einstellung gehalten |

Für 1 gibt es eine neue Wache: sie misst jede „async only"-Aussage in acht

Ob eine Zuweisung ankommt, fragte sie nicht, weil ich es nicht gefragt hatte.
